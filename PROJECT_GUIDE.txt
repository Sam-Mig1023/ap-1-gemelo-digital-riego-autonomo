5. FLUJO DE DATOS - CÓMO FUNCIONA EL SISTEMA
================================================================================

┌─────────────────────────────────────────────────────────────────────────────┐
│                     FLUJO DE UNA DECISIÓN DE RIEGO                         │
└─────────────────────────────────────────────────────────────────────────────┘

PASO 1: Lectura de Sensores
├─ Sensores IoT leen:
│   • Humedad del suelo (10cm, 30cm, 60cm)
│   • Temperatura del dosel (IRT)
│   • Déficit de presión de vapor (VPD)
│   • Intensidad de radar meteorológico
│   └─ Datos llegan a: apiClient.ts → ingestTelemetry()

PASO 2: Procesamiento
├─ anomalyDetectionEngine.ts
│   └─ Detecta lecturas anómalas (Isolation Forest)
├─ digitalTwinEngine.ts
│   └─ Simula estado hídrico del suelo
└─ Datos limpios y simulados listos

PASO 3: Inferencia RL
├─ rlAgentEngine.ts (frontend) simula:
│   • Ejecuta política PPO
│   • Genera recomendación de dosis
│   • Calcula confianza (0.0-1.0)
│   • Explica decisión (valores SHAP)
└─ Resultado: RLDecision → mostrar en UI

PASO 4: Aprobación Humana
├─ Agrónomo ve la decisión en RLDecisionConsole
├─ Puede: Aprobar / Rechazar / Anular manualmente
└─ Decisión aprobada se registra en auditoría

PASO 5: Ejecución
├─ IrrigationControl envía comando VRI
│   • PWM signals a válvulas
│   • Profundidad: mm
│   • Zona: 1-4
│   • Ventana: horario de tarifa optimizada
└─ Riego ejecutado en campo

PASO 6: Feedback del Loop Cerrado
├─ Después del riego se observan resultados:
│   • Nueva humedad del suelo
│   • Cambio en estrés hídrico
│   • Consumo de agua real vs predicho
└─ closedLoopController.ts calcula reward

PASO 7: Aprendizaje
├─ Experiencia registrada: (estado, acción, recompensa)
├─ Se acumula para reentrenamiento del modelo PPO
└─ Próxima vez la IA toma mejores decisiones

┌─────────────────────────────────────────────────────────────────────────────┐
│                        COMPONENTES PRINCIPALES                              │
└─────────────────────────────────────────────────────────────────────────────┘

1. GEMELO DIGITAL (Digital Twin)
   ├─ Simula dinámica hídrica del suelo
   ├─ Modelo: Green-Ampt (infiltración) + Balance hídrico
   └─ Entrada: Riego, lluvia → Salida: Humedad predicha

2. AGENTE RL (Reinforcement Learning Agent)
   ├─ Algoritmo: PPO (Proximal Policy Optimization)
   ├─ Entrada: Estado (sensores + digital twin)
   └─ Salida: Acción (dosis de riego recomendada)

3. XAI (eXplainable AI)
   ├─ Valores SHAP: Qué sensores influyeron en la decisión
   ├─ Reasoning text: Explicación en lenguaje natural
   └─ Confianza: Score de certeza (0-1)

4. CLOSED-LOOP
   ├─ Feedback: Resultado real vs predicción
   ├─ Reward: Métrica de éxito
   └─ Reentrenamiento: Mejora continua del modelo

5. RBAC & AUDITORÍA
   ├─ Roles: Superadmin, Agrónomo, Productor, Técnico, RL Agent
   ├─ Auditoría: Quién hizo qué y cuándo
   └─ SHA-256: Firma digital de cada operación

11. IMPLEMENTACIÓN TÉCNICA DE FASTAPI (BACKEND)
================================================================================

El backend sigue una arquitectura modular con FastAPI versionada (v1).
A continuación se explica CÓMO está implementado cada aspecto:

--------------------------------------------------------------------------------
11.1 PUNTO DE ENTRADA: /backend/app/main.py
--------------------------------------------------------------------------------

ESTRUCTURA BÁSICA:

  1. CREACIÓN DE LA APP:
        app = FastAPI(
            title="VRI Closed-Loop Digital Twin API",
            version="1.0.0",
            lifespan=lifespan,          # ← Gestión del ciclo de vida
            docs_url="/docs",            # ← Swagger UI automático
            redoc_url="/redoc"           # ← ReDoc alternativo
        )

     → lifespan() es un async context manager que ejecuta código al inicio
       y al apagado:
         - STARTUP: init_db() (inicializa pool de conexiones DB demo)
         - SHUTDOWN: close_db() (libera recursos)

  2. MIDDLEWARE CORS:
        app.add_middleware(
            CORSMiddleware,
            allow_origins=settings.CORS_ORIGINS,   # ["*"] en demo
            allow_credentials=True,
            allow_methods=["*"],
            allow_headers=["*"],
        )

     → Permite que el frontend en puerto 3000 haga peticiones al backend
       en puerto 8000 sin bloqueos de Same-Origin Policy. En producción:
       CORS_ORIGINS se limitaría a ["https://mi-app.com"].

  3. RUTEO VERSIONADO:
        app.include_router(api_router, prefix="/api/v1")

     → Todos los endpoints cuelgan de /api/v1. Si en el futuro se hace
       un breaking change, se crea v2 y se mantiene v1 por compatibilidad.

  4. HEALTH CHECK RAÍZ:
        @app.get("/health")
        async def health_check():
            return {"status": "healthy", "service": "...", "version": "..."}

     → Útil para Kubernetes livenessProbe / Docker healthchecks.

--------------------------------------------------------------------------------
11.2 CONFIGURACIÓN CENTRAL: /backend/app/core/config.py
--------------------------------------------------------------------------------

La clase Settings() lee variables de entorno con os.getenv(), con valores
default para DEMO. No usa pydantic-settings para mantenerlo simple.

PARÁMETROS IMPORTANTES:
  • DATABASE_URL:      postgresql+asyncpg://user:pass@host:5432/db
  • REDIS_URL:         redis://localhost:6379 (cache + Celery broker)
  • SECRET_KEY / ALGORITHM:  Para JWT (futura implementación OAuth2)
  • CORS_*:            Configuración de CORS
  • RL_MODEL_VERSION:  PPO-VRI-DualReward-v4.2 (tracking de modelo)
  • MAX_IRRIGATION_DEPTH_MM:  100.0 (hard safety limit)
  • REPORT_OUTPUT_DIR: ./reports (carpeta de descargas)

Singleton pattern:
  settings = Settings() → Se importa globalmente en todos los módulos.

11.3 BASE DE DATOS: /backend/app/core/database.py
--------------------------------------------------------------------------------

MODO DEMO (actual):
  - init_db() solo escribe logs: "Database initialization (demo mode)"
  - close_db() escribe logs.
  - No hay conexión real a PostgreSQL; los datos se generan in-line en
    cada endpoint.

MODO PRODUCCIÓN (a implementar según comentarios del archivo):
  - Motor asíncrono con SQLAlchemy 2.0 + asyncpg:
        engine = create_async_engine(settings.DATABASE_URL, pool_size=20)
  - AsyncSessionLocal con sessionmaker(expire_on_commit=False, class_=AsyncSession)
  - Función get_db() como FastAPI dependency injection:
        async def get_db():
            async with AsyncSessionLocal() as session:
                yield session
  - En los endpoints: db: AsyncSession = Depends(get_db)

EXTENSIONES POSTGRESL:
  • TimescaleDB: convierte tablas sensor_telemetry en hypertables con
    time_bucket() para agregados por minuto/hora/día (muy rápido).
  • PostGIS: columnas geometry(Point, 4326) para ubicación GPS de
    sensores y zonas (coberturas GIS).

11.4 RUTEO Y ENDPOINTS: /backend/app/api/v1/__init__.py + endpoints/*
--------------------------------------------------------------------------------

PATRÓN DE ROUTERS ANIDADOS:

  api_router (prefix: /api/v1)
  ├─ health.router     (tags: ["Health"])                → /health, /ready
  ├─ fields.router     (prefix:/fields, tags:["Fields"]) → GET /api/v1/fields...
  ├─ sensors.router    (prefix:/sensors)                 → Telemetría IoT
  ├─ rl_engine.router  (prefix:/rl-engine)               → Agente PPO RL
  ├─ irrigation.router (prefix:/irrigation)              → Control HW VRI
  └─ reports.router    (prefix:/reports)                 → Generación docs

Cada archivo de endpoint sigue este patrón:

  from fastapi import APIRouter
  router = APIRouter()                    # ← Crea router

  @router.get("/ruta", status_code=200)   # ← Decorador con método HTTP
  async def handler_func(param: Tipo):    # ← Validación Pydantic automática
      return result_dict                  # ← Respuesta JSON serializada

DETALLE DE ENDPOINTS POR MÓDULO:

  HEALTH (/api/v1)
    GET  /health   → 200 OK {"status": "healthy", "version": "1.0.0"}
    GET  /ready    → readiness check (DB + cache connected)

  FIELDS (/api/v1/fields)
    GET  /                      → Lista todos los AgriculturalField
    GET  /{field_id}            → Detalle de 1 campo: nombre, cultivo, área
    GET  /{field_id}/zones      → 4 ManagementZones con soil type + coords
    GET  /{field_id}/zones/{z}  → Zona individual + stats hidráulicos

  SENSORS (/api/v1/sensors)
    GET  /                      → Inventario de sensores (TDR, IRT, rain)
    GET  /{sensor_id}           → Metadata sensor: zona, tipo, calib date
    POST /telemetry/ingest      → BATCH ingest (body: [{ts, value, ...}])
    GET  /zone/{zone_id}        → Lecturas filtradas por zona (con rango
                                  de fechas query params: ?start=ISO&end=ISO)

  RL ENGINE (/api/v1/rl-engine)
    POST /infer-vri-rates       → Inferencia PPO: body={zoneId, observations}
                                  Retorna: decisionId, depthMm, shapValues[],
                                  confidence, executionWindow (22:00-04:00)
    GET  /decisions             → Historial paginado (?field_id=&status=)
    POST /decisions/{id}/approve    → body: {approvedBy: "Agrónomo X"}
    POST /decisions/{id}/override   → body: {depthMm, reason: "..."}
    POST /retrain-policy        → Trigger Celery task reentrenamiento PPO

  IRRIGATION (/api/v1/irrigation)
    POST /execute-decision      → Envía PWM a válvulas VRI por zona
    POST /manual-trigger        → Riego manual fuera de horario
    GET  /status                → Estado de válvulas, presión de agua
    GET  /schedule              → Próximos riegos en cola
    POST /emergency-stop        → Cierre inmediato de todas las válvulas

  REPORTS (/api/v1/reports)
    POST /generate              → {format: "pdf", sections: [...]} → taskId
    GET  /{id}/status           → progresivo: pending / processing / done
    GET  /{id}/download         → FileResponse (stream de bytes)
    GET  /history               → Historial de reportes generados
    POST /schedule              → Programación CRON (diaria/semanal)
    POST /what-if-export        → Exporta escenario de simulación a Excel
